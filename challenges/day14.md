## 📅 Day 14: Linux Process 트러블슈팅

### 1. Task

---

- **요구사항**: xFusionCorp Industries 프로덕션 지원 팀의 모니터링 시스템에서 감지된 Stratos DC 내 Apache 서비스 중단 문제를 해결한다. 장애가 발생한 호스트를 식별하여 서비스를 정상화하고, 인프라 내 모든 앱 서버의 Apache 가동 포트를 `5004`로 일괄 변경 및 고정한다.

- **대상**: Nautilus App 호스트 전수 (`stapp01`, `stapp02`, `stapp03`)

- **목표**:
  1. 각 앱 서버의 Apache 설정 파일(`/etc/httpd/conf/httpd.conf`)을 수동 편집하여 Listen 포트를 `5004`로 수정
  2. `5004` 포트를 선점하여 바인딩 에러(`Address already in use`)를 유발하는 유령 프로세스 식별 및 처단
  3. 모든 앱 호스트에서 Apache 서비스의 정상 가동(`active (running)`) 상태 및 부팅 시 자동 시작 설정 검증

### 2. Workflow

---

```text
[ Apache 수동 포트 수정 (vi) ] -> [ 5004 포트 충돌 발생 (Address already in use) ]
                                          |
                                          v
                            [ ss 명령어로 점유 중인 범인 PID 식별 ]
                                          |
                                          v
                            [ kill -9 명령어로 유령 프로세스 강제 종료 ]
                                          |
                                          v
[ Apache 포트 5004 바인딩 성공 ] ----> [ httpd 서비스 정상 기동 (Active) ]

```

### 3. 해결 과정 (Troubleshooting & Action)

---

#### 3-1. Apache 설정 파일 수동 편집 및 포트 전환

각 앱 서버에 순차적으로 접속하여 설정 파일을 직접 열어 포트를 변경한다.

```bash
# 1. 앱 서버 접속 및 루트 권한 획득 (예: stapp01)
ssh tony@stapp01
sudo su -

# 2. vi 편집기로 Apache 설정 파일 열기
vi /etc/httpd/conf/httpd.conf

# 3. [vi 편집 내부 작업] /Listen 으로 검색하여 기존 포트 라인을 찾은 뒤 Listen 5004 로 수정 후 저장 (:wq)

```

#### 3-2. 포트 충돌 프로세스 식별 및 강제 종료

수정 후 서비스 재시작 시 포트 중복 점유 에러가 발생하는 경우, 소켓 인터페이스 조회 도구를 통해 범인을 찾아 처단한다.

```bash
# 1. ss 명령어를 사용하여 현재 5004 포트를 점유 중인 프로세스(PID) 추적
ss -tulnp | grep 5004
# 출력 결과 확인: tcp LISTEN 0 511 *:5004 *:* users:(("httpd",pid=8575,fd=4),...)

# 2. 식별된 PID를 기반으로 5004 포트를 붙잡고 있던 유령 프로세스들을 강제 종료 (Kill)
kill -9 8575 8574 8573 8565

```

#### 3-3. 서비스 가동 및 인프라 무결성 검증

포트가 깨끗하게 비워진 것을 확인한 뒤 엔진을 재가동하여 정상 활성화 상태를 마친다.

```bash
# 1. Apache 서비스 재시작 및 자동 활성화 등록
systemctl restart httpd
systemctl enable httpd

# 2. httpd 서비스가 active (running) 상태로 정상 구동되는지 최종 검증
systemctl status httpd

```

_(동일한 프로세스로 `stapp01`, `stapp03` 노드에서도 설정 파일 수정 및 프로세스 클리닝을 완료하여 전체 인프라 서비스를 정상화함)_

### 4. 무엇을 배웠는가 (Takeaway)

---

- **포트 충돌 메커니즘 (`Address already in use`)**: 포트 충돌 에러는 **'내가 예약한 독서실 자리에 다른 사람이 이미 앉아있는 것'**과 같다. **하나의 포트(자리)에는 오직 하나의 프로세스(사람)만 앉을 수 있는데**, 고장 난 구형 프로세스가 자리를 비워주지 않고 버티면 새 서비스가 실행되지 못한다. 실무 인프라 관점에서는 무작정 서비스를 재시작하기 전에 네트워크 소켓 상태를 조회하여 포트 선점 여부를 파악하는 선제적 디버깅 능력이 필수적이다.

- **프로세스 및 소켓 제어 (`ss` & `kill`)**: `netstat` 대신 최신 리눅스 환경에서 권장되는 `ss` 명령어를 사용하여 네트워크 소켓과 연동된 범인의 정체(PID)를 정확히 알아내고 `kill -9`로 처리할 수 있다. 이는 '경찰이 불법 점거자를 식별하고 강제 퇴거 조치하는 것'과 같으며, 인프라 엔지니어는 시스템 자원을 마비시키는 좀비 프로세스를 적절히 제어하여 런타임 환경의 무결성을 지켜야 한다.
