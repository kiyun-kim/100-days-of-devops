## 📅 Day 26: Git Manage Remotes

### 1. Task

- **요구사항**: xFusionCorp 개발 팀의 인프라 변경 정책에 대응하여, 기존 로컬 Git 저장소에 신규 배포용 원격 저장소를 추가 연결하고 로컬의 최신 작업 소스 코드를 해당 원격지로 안전하게 마이그레이션 배포합니다.

- **목표**:
  1. Storage 서버(`ststor01`)의 로컬 저장소 경로 `/usr/src/kodekloudrepos/blog`로 이동합니다.
  2. `dev_blog`라는 명칭으로 신규 원격 저장소(Remote) 주소 `/opt/xfusioncorp_blog.git`를 추가 정의합니다.
  3. 로컬 내부로 임시 소스 파일 `/tmp/index.html`을 이주한 후 `master` 브랜치에 스냅샷을 생성합니다.
  4. 최종 통합된 로컬 이력을 새로 추가한 `dev_blog` 원격 저장소의 `master` 브랜치로 푸시(Push)합니다.

---

### 2. Workflow

```text
  [기존 원격지: origin]
          ▲
          │ (연결 유지)
  [로컬 저장소: blog]  ──(git remote add)──>  [신규 원격지: dev_blog]
          │                                             ▲
          ├─> [/tmp/index.html 복사 & 커밋]             │
          │                                             │
          └──────────────────(git push dev_blog master)-┘

```

---

### 3. 해결 과정 (Action)

#### 3-1. 저장소 진입 및 신규 원격지(Remote) 매핑

다중 사용자 인프라 환경의 소유권 경고(`dubious ownership`)를 차단하기 위해 `sudo` 권한을 활용하여 안전하게 새 개발용 원격 저장소를 트랙에 추가합니다.

```bash
# 배포 대상 로컬 Git 저장소 디렉토리로 이동합니다.
cd /usr/src/kodekloudrepos/blog

# 신규 원격 저장소 명칭인 dev_blog와 해당 파일 시스템 원격 경로를 바인딩합니다.
sudo git remote add dev_blog /opt/xfusioncorp_blog.git

# 등록된 원격 저장소 목록과 Fetch/Push 주소 권한을 교차 검증합니다.
sudo git remote -v

```

#### 3-2. 소스 파일 이주 및 로컬 형상 최신화

운영 스크립트 배포를 위해 지정된 정적 인프라 파일을 로컬 저장소 내 수동 동기화하고 커밋을 기록합니다.

```bash
# /tmp/index.html 파일을 현재 블로그 로컬 저장소 루트 경로(.)로 복사합니다.
sudo cp /tmp/index.html .

# 복사된 신규 파일을 Git 인덱스 영역(Staging Area)에 추가합니다.
sudo git add index.html

# master 브랜치 위에 배포 버전을 식별할 수 있는 커밋 스냅샷을 발행합니다.
sudo git commit -m "Add index.html and update production release"

```

#### 3-3. 신규 타겟 원격 저장소 배포 (Push)

기존의 기본 원격지(`origin`)가 아닌, 새롭게 이주 타겟으로 지정된 `dev_blog` 원격지로 명시적 푸시를 수행합니다.

```bash
# 로컬의 최신 master 브랜치 이력을 새로 정의한 dev_blog 원격지로 영구 전송합니다.
sudo git push dev_blog master

# 최종 작업 완료 후 파일 시스템 작업 트리가 깨끗한 상태(clean)인지 재차 검증합니다.
sudo git status

```

### 4. 핵심 개념 정리

- **Git 원격 저장소 (Git Remote)**: 네트워크나 로컬 파일 시스템 상의 다른 위치에 존재하는 프로젝트의 복사본(저장소)입니다. 하나의 로컬 저장소는 기본값인 `origin` 외에도 여러 개의 원격 저장소를 동시에 가질 수 있어, 목적(개발, 검증, 운영 등)에 따른 다중 배포 파이프라인 구축을 가능하게 합니다.
  💡 **비유하자면**, 내가 작성한 책 원고를 보관하는 "메인 출판사(origin)"가 이미 있는 상태에서, 신규 지점인 "지방 분점(dev_blog)"과 새로 계약하여 원고 배송 라인을 하나 더 개설한 것과 같습니다. 이제 나는 필요에 따라 원하는 출판사(Remote)를 콕 집어서 원고(Commit)를 트럭에 실어 보낼(Push) 수 있게 됩니다.

- **Git 스테이징 영역 (Staging Area / Index)**: 작업 디렉토리(Working Directory)와 Git 저장소(Repository) 사이에 존재하는 가상의 준비 영역입니다. `git add` 명령어를 통해 다음 커밋에 포함할 변경 사항들만 선별적으로 기록하는 완충 지대 역할을 수행합니다.
  💡 비유하자면, 이삿짐을 트럭에 싣기 전에 "현관문 앞에 따로 모아두는 박스들"과 같습니다. 방 안의 모든 물건을 한꺼번에 트럭에 던져 넣는 것이 아니라, 이번에 옮길 핵심 물건들만 박스에 차곡차곡 분류하여 담아두는 준비 단계입니다.

### 5. 무엇을 배웠는가 (Takeaway)

- **실무 관점의 의의**: 프로덕션 환경이나 대규모 기업형 MLOps 인프라에서는 단일 원격 저장소만 사용하는 경우가 드뭅니다. 내부 검증용 온프레미스 Git 저장소, 외부 클라우드 백업용 저장소, 스테이징 및 프로덕션 환경을 격리한 다중 타겟 배포 파이프라인이 유기적으로 가동됩니다. 이번 실습은 이처럼 하나의 소스 코드를 목적지별로 안전하게 라우팅하여 멀티 테넌트 타겟에 병렬적으로 배포할 수 있는 인프라의 기본 확장 능력을 보여줍니다.

- **다중 원격 파이프라인 설계 구조 이해**: 인프라 배포 환경에서 단일 중앙 저장소 구조에 의존하지 않고, 목적에 따라 원격지 주소를 유연하게 분리 배정(`git remote add`)하여 멀티 테넌트 타겟에 병렬적으로 형상을 배포할 수 있는 아키텍처적 유연성을 체득했습니다.
