## 📅 Day 29: Manage Git Pull Requests

### 1. Task

- **요구사항**: `master` 브랜치의 무결성을 보호하기 위해 일반 개발자의 직접적인 푸시(Push)를 제한하고, 웹 기반 Git 호스팅 포털에서 분기 브랜치의 변경 사항을 풀 리퀘스트(PR) 및 할당된 Reviewer(검역자)의 교차 승인을 거쳐 프로덕션 환경에 최종 병합합니다.

- **목표**:
  1. `Gitea 웹 UI`에 개발자 `max` 계정으로 로그인하여 `sarah/story-blog` 저장소로 진입합니다.
  2. `master` 브랜치를 대상(Destination)으로 하고 `story/fox-and-grapes` 브랜치를 출발지(Source)로 하는 풀 리퀘스트를 생성합니다.
  3. PR 제목을 명세서 규격인 `Added fox-and-grapes story`로 정확히 기입하고, 리뷰어로 `tom`을 할당합니다.
  4. `tom` 계정으로 교체 로그인하여 전송된 소스 코드를 최종 검토 및 승인(Approve)한 뒤, **Merge Pull Request**를 트리거하여 메인 형상에 완벽히 병합합니다.

---

### 2. Workflow

```text
[Gitea 포털: max 로그인] ──> [sarah/story-blog 진입] ──> [New PR 개설]
                                                            │
                                                            ▼ (Reviewer: tom 지정)
[Gitea 포털: tom 로그인] ──> [Pull Request #1 검토] ──> [Create Merge Commit]
                                                            │
                                                            ▼
                                                [master 브랜치 병합 완료]

```

---

### 3. 해결 과정 (Action)

#### 3-1. Max 계정 기반의 코드 검역(PR) 발송 및 리뷰어 바인딩

개발자 권한 계정으로 원격 저장소에 접근하여 배포 대상 브랜치 브리지를 설정하고 검토 파이프라인을 활성화합니다.

1. Gitea 웹 콘솔에 `max` 계정으로 로그인 후 `sarah/story-blog` 저장소의 **[Pull Requests]** 탭으로 이동하여 [New Pull Request]를 선언합니다.
2. 브랜치 타겟팅 규칙을 `Target: master` ◀ `Source: story/fox-and-grapes` 구도로 명시적 매핑합니다.
3. PR 개설 양식의 Title 필드에 지정된 규격 명칭인 `Added fox-and-grapes story`를 공백 및 오타 없이 기입합니다.
4. 우측 사이드바의 **[Reviewers]** 제어 폼을 활성화하여 조직 내 Reviewer인 `tom`을 찾아 클릭함으로써 리뷰 권한을 할당(Assign)하고 PR 생성을 완료합니다.

#### 3-2. 검토자 계정 전환 및 최종 승인 병합 (Merge)

상위 검역 권한을 가진 엔지니어 계정으로 컨텍스트를 스위칭하여 코드 무결성을 증명하고 프로덕션 라인에 결합합니다.

1. 오른쪽 상단 프로필 메뉴를 호출하여 기존 `max` 계정을 **[Sign Out]** 처리합니다.
2. Reviewer 계정인 유저네임 **`tom`** (패스워드: `Tom_pass123`) 정보를 입력하여 포털에 다시 로그인합니다.
3. 대시보드에 활성화된 `Added fox-and-grapes story` 풀 리퀘스트 세션으로 재진입합니다.
4. 하단의 커밋 내역과 변경 파일 레이어를 정밀 검토한 뒤, **[Merge Pull Request]** 및 **[Create Merge Commit]** 버튼을 연속 트리거하여 배포 파이프라인을 **Merged**로 최종 안착시킵니다.

### 4. 핵심 개념 정리

- **풀 리퀘스트 (Pull Request - PR)**: 독립된 브랜치에서 수정한 코드를 메인 코드 줄기(master)에 병합하기 전, 동료 개발자 및 아키텍트들에게 "내가 수정한 코드를 가져가서 병합해 달라"고 정식으로 요청하는 코드 리뷰 및 형상 관리 프로세스입니다.
  💡 비유하자면, 자동차 제조 공장에서 임시 작업실(Source 브랜치)의 엔지니어가 새로 개발한 "엔진 부품(변경 커밋)"을 실제 조립 라인(Target master 브랜치)에 끼워 넣기 전에, 공장 전체 도면을 망가뜨리지 않는지 확인받으려고 결재판에 "부품 조립 승인 요청서(PR)"를 올려두는 행위와 같습니다.

- **코드 리뷰어 (Code Reviewer)**: 풀 리퀘스트로 제출된 소스 코드의 아키텍처, 버그 가능성, 보안 취약점, 인프라 명세 오타 등을 메인 형상에 반영하기 전에 최종 검역하고 승인(Approve) 또는 반려할 수 있는 권한을 가진 검토자입니다.
  💡 비유하자면, 앞서 엔지니어가 제출한 조립 승인 요청서를 꼼꼼히 읽어보고 규격에 맞는지 부품을 직접 자로 재본 뒤, 최종 조립을 허가하며 합격 도장을 쾅 찍어주는 "공장 수석 검수관(Tom)"과 같습니다. 검수관의 도장 없이는 아무리 좋은 부품이라도 메인 조립 라인에 들어갈 수 없습니다.

---

### 5. 무엇을 배웠는가 (Takeaway)

- **실무 관점의 의의**: 실제 기업용 엔터프라이즈 환경 및 프로덕션 CI/CD 파이프라인에서는 보안 컴플라이언스 및 소스 코드 무결성 방어를 위해 메인 브랜치에 직접 푸시(`git push origin master`)하는 행위를 브랜치 보호 정책(Branch Protection Rule)으로 원천 차단합니다. 이번 공정을 통해 실무 Git-Flow 모델에서 요구하는 PR 생성, 리뷰어 할당, 권한 분리(Separation of Duties) 기반 교차 검역 체계의 엔드투엔드 거버넌스 아키텍처를 완벽하게 체득했습니다.
