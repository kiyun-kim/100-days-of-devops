## 📅 Day 32: Git Feature 브랜치 Rebase 및 충돌 대응

### 1. Task

- **요구사항**: Stratos 데이터 센터의 Storage 서버 내 Git 프로젝트 저장소(`/usr/src/kodekloudrepos`)에서 작업 중인 개발자의 요청에 따라, `feature` 브랜치를 최신 `master` 브랜치 기준점으로 리베이스(Rebase)하여 불필요한 머지 커밋 없이 커밋 히스토리를 깔끔하게 정렬하고 원격 저장소에 반영해야 합니다.

- **목표**:
  1. Storage 서버(`ststor01`)의 `natasha` 계정으로 접속하여 해당 Git 저장소 경로로 이동합니다.
  2. 개발자가 작업 중인 로컬 `feature` 브랜치로 전환합니다.
  3. 원격 저장소(`origin/master`)의 최신 변경 사항을 가져와 로컬 브랜치의 기준점을 한 줄기로 정렬하는 Rebase 작업을 수행합니다.
  4. 리베이스로 인해 변형된 커밋 히스토리를 원격 저장소(`origin`)의 `feature` 브랜치에 강제 푸시(`--force`)하여 최종 동기화를 완료합니다.

---

### 2. Workflow

```text
[리베이스 실행 전 히스토리]
origin/master  :  A ─── B ─── C (최신 메인 라인)
                       └─── D ─── E (개발자의 feature 브랜치)

                           (git rebase 실행)
                                   ▼
[리베이스 완료 후 히스토리]
origin/master  :  A ─── B ─── C (마스터 최신 커밋이 베이스가 됨)
                               └─── D' ─── E' (선형 정렬된 feature 브랜치)

                       (git push --force origin feature)
                                   ▼
[원격 저장소 반영] Remote Repository(/opt/apps.git)에 깔끔한 히스토리로 동기화 완료

```

---

### 3. 해결 과정 (Action)

#### 3-1. 저장소 이동 및 브랜치 전환

Storage 서버에 접속한 후, 실제 프로젝트가 관리되고 있는 Git 저장소 디렉터리로 이동하여 작업 대상 브랜치로 전환합니다.

```bash
# 지정된 Git 저장소 디렉터리로 이동
cd /usr/src/kodekloudrepos

# 전체 브랜치 상태(로컬 및 원격)를 모니터링하여 대상 식별
sudo git branch -a

# 작업을 진행할 feature 브랜치로 체크아웃
sudo git checkout feature

```

#### 3-2. 원격 이력 동기화 및 Rebase 수행

원격 저장소의 최신 변경 사항을 로컬로 가져온 뒤, 불필요한 머지 커밋을 남기지 않기 위해 마스터 브랜치 기반으로 리베이스를 진행합니다.

```bash
# 원격 저장소(origin)의 최신 메타데이터 및 브랜치 상태 갱신
sudo git fetch origin

# 로컬 feature 브랜치의 공통 조상을 원격 마스터(origin/master)의 최신 커밋으로 재설정
sudo git rebase origin/master

```

#### 3-3. 원격 저장소 강제 푸시 완료

Rebase 작업은 커밋 해시 자체를 새롭게 재작성하므로, 일반적인 push는 원격 저장소에서 거부(`non-fast-forward`)됩니다. 역사를 올바르게 맞추기 위해 강제 푸시를 적용합니다.

```bash
# 리베이스로 재정렬된 feature 브랜치 이력을 원격 저장소에 강제 반영
sudo git push origin feature --force

```

---

### 4. 핵심 개념 정리

- **Git Rebase**: 브랜치의 공통 조상이 되는 베이스(Base) 커밋 포인트를 다른 브랜치의 최신 커밋 위치로 변경하여, 커밋 히스토리의 줄기를 깨끗하게 재작성하는 명령어입니다.

  > 💡 다른 필기 노트(`feature`)에 따로 작성 중이던 요약본을, 교과서의 최신 개정판(`master`) 뒷부분에 자연스럽게 이어 붙여서 처음부터 한 권의 책이었던 것처럼 목차를 깔끔하게 정렬하는 것과 같습니다.

- **Forced Push (`--force`)**: 로컬 저장소의 커밋 히스토리가 원격 저장소의 히스토리와 일치하지 않고 충돌할 때, 원격의 거부 검증 절차를 우회하고 로컬의 상태로 강제 덮어쓰기하는 옵션입니다.

  > 💡 문서 수정 과정에서 순서가 완전히 뒤바뀌어 결재 시스템이 승인을 거부할 때, 최고 관리자가 책임지고 기존 원격 문서를 파쇄한 뒤 새 문서로 강제 교체 도장을 찍는 것과 같습니다.

---

### 5. 무엇을 배웠는가 (Takeaway)

- **실무 관점의 의의**: 다수의 엔지니어가 협업하는 프로덕션 환경에서 의미 없는 머지 커밋(`Merge branch 'master' of ...`)이 수백 개씩 쌓이면 히스토리 추적 능력이 저하됩니다. Rebase를 활용해 선형적(Linear)인 커밋 로그를 유지하는 습관은 소스코드 가독성을 높이고 향후 기능 역추적(Rollback)을 용이하게 만드는 중요한 형상 관리 표준입니다.

- **엔지니어링 인사이트**: 리베이스 후 발생하는 `non-fast-forward` 에러는 시스템이 고장 난 것이 아니라 이력 변형에 따른 자연스러운 거부 반응임을 인지했습니다. 원격 저장소와의 매핑 상태를 정확히 추적하고, 필요한 상황에서 `--force` 옵션을 적재적소에 활용하여 형상 관리를 정렬하는 통제 역량을 다질 수 있었습니다.
