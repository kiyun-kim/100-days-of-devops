## 📅 Day 38: Pull Docker Image

### 1. Task

- **요구사항**: Nautilus 개발 팀의 새로운 애플리케이션 테스트 환경 구성을 위해, 지정된 애플리케이션 서버에 필요한 Docker 베이스 이미지를 다운로드하고 프로젝트 명세에 맞춘 새로운 태그(이름표)를 할당해야 합니다.

- **목표**:
  1. App Server 2(`stapp02`, 계정: `steve`)에 접속합니다.
  2. 도커 레지스트리로부터 `busybox:musl` 이미지를 로컬 서버로 Pull 합니다.
  3. 다운로드한 이미지에 `busybox:news`라는 새로운 커스텀 태그를 부여합니다.
  4. 원본 이미지와 새 태그가 부여된 이미지가 동일한 식별자(Image ID)를 공유하는지 검증합니다.

---

### 2. Workflow

```text
[Docker Hub / Registry]
          │
  (docker pull)
          │
          ▼
[App Server 2 (stapp02) Local Storage]
busybox:musl (ID: 5a93558ae921)
          │
   (docker tag)
          │
          ▼
busybox:news (ID: 5a93558ae921) ─> 동일한 이미지 레이어 공유

```

---

### 3. 해결 과정 (Action)

#### 3-1. 대상 서버 접속

작업 대상인 App Server 2로 원격 접속을 진행합니다.

```bash
# App Server 2로 SSH 접속 (계정: steve)
ssh steve@stapp02
# 비밀번호 입력: Am3ric@

```

#### 3-2. 베이스 이미지 다운로드

테스트에 필요한 경량화 리눅스 유틸리티 이미지인 `busybox:musl`을 서버로 가져옵니다.

```bash
# 지정된 태그(musl)의 busybox 이미지를 다운로드
sudo docker pull busybox:musl

```

#### 3-3. 이미지 리태깅 (Re-tag)

파이프라인이나 개발팀의 요구사항에 맞춰 동일한 이미지에 새로운 이름표(`news`)를 하나 더 붙여줍니다.

```bash
# 기존 이미지에 'news'라는 새로운 태그를 부여
sudo docker tag busybox:musl busybox:news

```

#### 3-4. 이미지 및 태그 상태 검증

두 태그가 정상적으로 생성되었고, 스토리지 낭비 없이 같은 이미지를 바라보고 있는지 식별자(IMAGE ID)를 확인합니다.

```bash
# 로컬에 저장된 busybox 관련 이미지 목록 조회
sudo docker images | grep busybox

```

_(조회 결과 `musl`과 `news` 태그 모두 `5a93558ae921`라는 동일한 IMAGE ID를 공유하는 것을 확인)_

---

### 4. 핵심 개념 정리

- **`docker pull`**: 원격 컨테이너 레지스트리(예: Docker Hub, AWS ECR)에서 완성된 이미지 레이어들을 현재 서버의 로컬 스토리지로 다운로드하는 명령어입니다.
- **`docker tag`**: 기존에 존재하는 이미지에 새로운 레포지토리 이름이나 버전(Tag)을 부여하는 명령어입니다.
  > 💡 **비유하자면**, 파일 자체를 복사해서 용량을 2배로 늘리는 것이 아니라, 이미 존재하는 파일(이미지 레이어)에 윈도우의 '바로가기'나 리눅스의 '하드 링크'처럼 새로운 **이름표(포인터)**만 하나 더 달아주는 것과 같습니다.

---

### 5. 무엇을 배웠는가 (Takeaway)

- **용량 걱정 없는 '이름표 달기'의 마법**: 처음 컨테이너를 다룰 때 `docker tag` 명령어를 쓰면 1.5GB짜리 이미지가 복사되어 용량을 두 배로 차지하는 줄 알고 조마조마했던 기억이 있습니다. 하지만 오늘 `docker images` 결과를 통해 두 태그(`musl`, `news`)가 완벽히 동일한 IMAGE ID를 공유하는 것을 직접 눈으로 확인했습니다. 물리적 스토리지 낭비 없이 논리적인 식별자만 무한정 늘릴 수 있다는 점이 도커 레이어 아키텍처의 진짜 매력임을 실감했습니다.

- **태그 관리가 곧 CI/CD 파이프라인의 생명줄**: 실무에서는 퍼블릭 레지스트리에서 받아온 이미지를 그대로 쓰기보다, 사내 프라이빗 레지스트리 주소를 앞에 붙이거나(`my-ecr.com/busybox:news`) 배포 버전을 명시하기 위해 리태깅(Re-tag)을 밥 먹듯이 하게 됩니다. 이 텍스트 몇 글자짜리 '이름표'를 제대로 관리하지 않으면 엉뚱한 구버전이 상용 서버에 배포되는 끔찍한 휴먼 에러를 겪게 됩니다. 단순해 보이는 명령어지만, "태그 관리가 꼬이면 배포가 꼬인다"는 현장의 뼈저린 교훈을 예방하는 필수 기본기임을 되새겼습니다.
