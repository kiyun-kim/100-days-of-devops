## 📅 Day 43: Nginx 기반 애플리케이션 컨테이너 배포 및 포트 매핑 구성

### 1. Task

- **요구사항**: Nautilus DevOps 팀의 애플리케이션 호스팅 계획에 따라, 안정성이 검증된 Nginx 웹 서버 환경을 컨테이너 기반으로 구축하고 외부 네트워크와 통신할 수 있도록 포트 포워딩을 구성합니다.

- **목표**: Stratos DC 내부의 Application Server 1 환경에 접근하여 지정된 Nginx 이미지를 다운로드하고, 요구사항에 맞는 컨테이너를 백그라운드로 실행합니다.
  1. 대상 서버인 App Server 1 (`stapp01`)에 SSH 원격 접속을 수행합니다.
  2. `nginx:stable` 도커 이미지를 호스트 시스템으로 Pull 합니다.
  3. `ecommerce`라는 명칭으로 컨테이너를 생성하고 백그라운드(Running state)로 실행합니다.
  4. 호스트 서버의 `6000` 포트를 컨테이너 내부의 `80` 포트로 매핑하여 통신을 연결합니다.

---

### 2. Workflow

```text
  [ External Traffic ]
          │ (TCP Port 6000)
          ▼
  [ App Server 1 (Host: stapp01) ]
          │
          │ (Port Mapping: 6000 -> 80)
          ▼
  [ Docker Daemon ]
          │
          └── [ Container: ecommerce ]
                  │
                  └── Image: nginx:stable
                  └── Service: Nginx Web Server (TCP Port 80)

```

---

### 3. 해결 과정 (Action)

#### 3-1. App Server 1 원격 접속

작업 대상인 App Server 1(`stapp01`)에 엔지니어 계정으로 접속하여 인프라 제어 환경을 준비합니다.

```bash
# Jump Host에서 App Server 1 서버로 SSH 원격 접속 실행
ssh tony@stapp01

```

#### 3-2. 지정된 Nginx 이미지 다운로드

요구사항에 명시된 안정화 버전(`stable` 태그)의 Nginx 공식 이미지를 로컬 레지스트리로 가져옵니다.

```bash
# nginx:stable 이미지 pull
sudo docker pull nginx:stable

```

#### 3-3. 컨테이너 백그라운드 실행 및 포트 매핑 적용

다운로드한 이미지를 기반으로 `ecommerce` 컨테이너를 생성합니다. 이때 `-d` 옵션으로 백그라운드 실행을 유지하고, `-p` 옵션으로 호스트와 컨테이너 간의 네트워크 포트를 연결합니다.

```bash
# ecommerce 컨테이너 실행 및 호스트 6000 포트를 컨테이너 80 포트로 매핑
sudo docker run -d --name ecommerce -p 6000:80 nginx:stable

```

#### 3-4. 실행 상태 및 바인딩 검증

컨테이너가 비정상 종료 없이 `Up` 상태를 유지하고 있는지, 그리고 지정한 포트 포워딩 규칙이 정확하게 바인딩되었는지 프로세스 목록을 통해 확인합니다.

```bash
# 실행 중인 컨테이너 상태(Up) 및 포트 매핑(0.0.0.0:6000->80/tcp) 확인
sudo docker ps | grep ecommerce

```

---

### 4. 핵심 개념 정리

- **Port Mapping (포트 매핑/포워딩)**: 컨테이너가 기본적으로 가지는 격리된 네트워크 환경을 외부와 연결하기 위해, 호스트 머신의 특정 포트로 인입되는 네트워크 트래픽을 컨테이너 내부의 지정된 포트로 전달(Forwarding)하는 네트워크 기술입니다.

  > 💡 비유하자면, 대형 오피스 빌딩(호스트)의 6000번 우편함으로 도착한 우편물을 특정 입주사(컨테이너)의 80번 책상으로 분류하여 정확하게 전달해 주는 사내 우편 자동 분류 시스템과 같습니다.

- **Detached Mode (`-d`, 백그라운드 실행)**: 도커 컨테이너를 실행할 때 현재 터미널의 포그라운드(Foreground) 세션을 점유하지 않고, 시스템 백그라운드 환경에서 독립적인 데몬(Daemon) 형태로 컨테이너를 구동시키는 실행 옵션입니다.

  > 💡 비유하자면, 식당에서 요리사에게 주문을 넣은 뒤 주방에서 요리가 완성될 때까지 그 자리에 서서 기다리는 대신, 주문만 전달하고 매니저(사용자)는 즉시 다른 테이블의 손님을 응대하러 이동할 수 있게 하는 업무 분담 방식과 같습니다.

- **Docker Image Tag (도커 이미지 태그)**: 동일한 소프트웨어 이미지 내에서도 특정 버전, 빌드 환경, 또는 릴리즈 상태(예: `latest`, `stable`, `alpine` 등)를 식별하고 관리하기 위해 이미지 이름 뒤에 콜론(`:`)으로 구분하여 부여하는 레이블입니다.
  > 💡 비유하자면, 동일한 공장에서 생산된 자동차 모델이라도 '프로토타입'이 아닌, 도로 주행 테스트를 모두 통과하여 안전성이 입증된 '정식 출고용 모델' 딱지를 명확하게 붙여놓은 것과 같습니다.

### 5. 무엇을 배웠는가 (Takeaway)

- **회고(Retrospective)**: 컨테이너 기반 환경에서 서비스를 배포할 때, 포트 매핑(`-p`)을 통해 내부의 서비스를 외부로 어떻게 노출할 것인지 명확히 설계하는 과정의 중요성을 체감했습니다. 이 개념이 없다면 컨테이너가 아무리 잘 실행되어도 외부 사용자는 해당 서비스에 절대 접근할 수 없는 고립된 환경이 되어버린다는 점을 다시 한번 각인하게 되었습니다.

- **Pain Point**: 실무 환경에서는 컨테이너를 실행하기 전 호스트 서버의 6000번 포트가 이미 다른 프로세스에 의해 점유되어 있지는 않은지 확인하는 과정이 필수적입니다. 이를 간과하고 맹목적으로 배포 스크립트를 실행할 경우 `port is already allocated`와 같은 에러를 마주하며 롤백해야 하는 리소스 낭비가 발생할 수 있습니다.

- **성장 포인트**: 단순히 "컨테이너를 띄우는 것"을 넘어, 네트워크 트래픽이 호스트의 어떤 인터페이스를 거쳐 컨테이너 내부의 애플리케이션으로 흘러가는지에 대한 '트래픽 파이프라인'을 논리적으로 추적하고 통제할 수 있는 시야를 갖추게 되었습니다. 향후 방화벽 설정이나 로드밸런서 연동 시 더욱 프로페셔널한 아키텍처 구성이 가능해질 것입니다.
