## 📅 Day 46: Docker Compose를 활용한 PHP-Apache 웹 서버 및 MariaDB 멀티 컨테이너 스택 연동 구축

### 1. Task

- **요구사항**: Nautilus 애플리케이션 개발 팀에서 개발 완료한 웹 블로그 서비스를 컨테이너화된 플랫폼에 안전하게 배포하기 위해, 운영 환경 이관 전 단일 호스트 내에서 독립된 가상 네트워크를 통해 웹 서버와 관계형 데이터베이스(RDBMS)가 상호 통신할 수 있도록 통합 멀티 컨테이너 스택을 구축하고 검증합니다.

- **목표**: Stratos DC 내부의 Application Server 1 (`stapp01`) 환경에 접근하여 사양서에 명시된 볼륨 영속성 및 환경 변수 조건들을 완벽하게 충족하는 선언적 정의 파일(YAML)을 생성하고 구동합니다.
  1. 대상 서버인 App Server 1 (`stapp01`)에 SSH 원격 접속을 수행합니다.
  2. 명시된 정확한 경로인 `/opt/devops/docker-compose.yml` 파일에 멀티 컨테이너 설계를 코딩합니다.
  3. `web` 서비스(`php:8.2-apache` 이미지, 컨테이너명 `php_blog`, 포트 3004:80, 볼륨 `/var/www/html` 마운트)를 정의합니다.
  4. `db` 서비스(`mariadb:latest` 이미지, 컨테이너명 `mysql_blog`, 포트 3306:3306, 볼륨 `/var/lib/mysql` 마운트)를 정의하고, `database_blog` 데이터베이스 및 `root`를 제외한 커스텀 사용자와 비밀번호 환경 변수를 주입합니다.
  5. 스택 기동 후 로컬 웹 포트(`3004`) 수신 상태를 점검하여 최종 무결성을 입증합니다.

---

### 2. Workflow

```text
  [ Client / Curl Request ]
              │ (TCP Port 3004)
              ▼
  [ App Server 1 (Host: stapp01) ]
              │
      ┌───────┴────────────────────────────────────────┐
      │  [ Docker Compose Engine Stack: /opt/devops ]  │
      │                                                │
      │   [ Service: web ]         [ Service: db ]     │
      │   - Container: php_blog    - Container: mysql_blog
      │   - Port: 3004 ──> 80      - Port: 3306 ──> 3306
      │         │                        │             │
      └─────────┼────────────────────────┼─────────────┘
                ▼ (Bind Mount)           ▼ (Bind Mount)
         /var/www/html            /var/lib/mysql
         (Host Storage)           (Host Storage)

```

### 3. 해결 과정 (Action)

#### 3-1. 작업 대상 서버 원격 접속 및 런타임 경로 구축

인프라 관리 인입점인 App Server 1에 안전하게 원격 접속한 뒤, 명세서가 지정한 전용 오케스트레이션 관리 디렉터리를 구성합니다.

```bash
# Jump Host에서 App Server 1 서버로 SSH 원격 접속 실행
ssh tony@stapp01

# 형상 관리 파일을 격리 배치하기 위한 전용 디렉터리 생성 및 이동
sudo mkdir -p /opt/devops
cd /opt/devops

```

#### 3-2. 선언적 멀티 서비스 구조 정의 (`docker-compose.yml`)

웹 서비스와 데이터베이스 간의 네트워크 격리, 볼륨 바인딩, 인증 자격 증명(Credentials)을 야믈 스크립트로 설계합니다.

```bash
# 지정된 경로 내에 정확한 파일명으로 명세서 정의 시작
sudo vi docker-compose.yml

```

```yaml
services:
  web:
    image: php:8.2-apache
    container_name: php_blog
    ports:
      - '3004:80'
    volumes:
      - /var/www/html:/var/www/html
    depends_on:
      - db

  db:
    image: mariadb:latest
    container_name: mysql_blog
    ports:
      - '3306:3306'
    volumes:
      - /var/lib/mysql:/var/lib/mysql
    environment:
      MYSQL_DATABASE: database_blog
      MYSQL_USER: blog_admin
      MYSQL_PASSWORD: ComplexPassword123!
      MYSQL_ROOT_PASSWORD: MegaRootPassword999!
```

- **설정 변경 의도**:
- `web` 서비스의 포트를 외부 `3004`번으로 열어 가용성을 확보하고, 정적 코드가 유실되지 않도록 호스트의 `/var/www/html`을 미러링 마운트했습니다. `depends_on` 구조를 선언하여 DB 서비스가 먼저 기동된 후 웹이 순차 배치되도록 안정성을 높였습니다.
- `db` 서비스는 MariaDB 최신 이미지 아키텍처를 기반으로 기동하되, 호스트 스토리지 영역인 `/var/lib/mysql`에 이식하여 컨테이너 붕괴 시에도 데이터가 원천 보존되도록 영속성을 설계했습니다. 규격에 따라 `root` 사용자를 배제한 커스텀 커넥션 계정(`blog_admin`) 및 패스워드를 환경 변수로 직접 주입했습니다.

#### 3-3. 선언적 컨테이너 스택 일괄 자동화 구동

통합 배치 스크립트를 도커 컴포즈 오케스트레이션 엔진에 로드하여 두 서비스를 백그라운드 상에 원클릭 정렬시킵니다.

```bash
# 최신 컴포즈 플러그인을 활용하여 전체 서비스 백그라운드 일괄 기동
sudo docker compose up -d

```

#### 3-4. 엔드포인트 트래픽 바인딩 및 통신 무결성 검증

도커 데몬의 프로세스 생성 로그를 대조하고, 호스트 루프백 주소의 `3004` 포트로 웹 요청(HTTP GET)을 송출하여 정상적인 인프라 작동을 확인합니다.

```bash
# 생성된 가상 네트워크 내부의 php_blog 및 mysql_blog 가동 상태 트래킹
sudo docker ps

# 로컬 런타임 엔드포인트로 커맨드 라인 웹 요청을 전달하여 서비스 수신 검증
curl http://localhost:3004/

```

### 4. 핵심 개념 정리

- **Multi-Container Stack (멀티 컨테이너 스택)**: 단일 애플리케이션 서비스를 구동하기 위해 결합한 웹 서버, WAS, DB, 캐시 등 고유의 역할을 가진 독립된 가상 컨테이너 그룹을 하나의 논리적 인프라 단위로 묶어 연동하고 제어하는 애플리케이션 아키텍처 아키타입입니다.

  > 💡 비유하자면, 푸드트럭 한 대에서 조리, 계산, 서빙을 직원이 혼자 다 처리하다가(단일 컨테이너), 규모가 커져서 정식 매장을 열고 주방 전문 조리 파트(`db`)와 홀 서빙 및 안내 데스크 파트(`web`)로 역할을 명확히 분리하되, 무전기(가상 네트워크)로 서로 실시간 소통하며 하나의 유기적인 식당(스택)을 운영하는 것과 같습니다.

- **`depends_on` (서비스 의존성 제어 지시어)**: Docker Compose 환경에서 특정 컨테이너들이 무작위로 실행되어 통신이 예기치 않게 단절되는 현상을 방지하기 위해, 컨테이너 간의 격리된 실행 순서 및 생명 주기 종속성을 논리적으로 고정해 주는 오케스트레이션 제어 옵션입니다.

  > 💡 비유하자면, 건물을 지을 때 기초 콘크리트 공사(DB)가 완전히 굳어 땅이 다져지기도 전에 성급하게 인테리어 가구와 간판(Web)을 먼저 들이밀다가 건물이 무너지는 배포 사고를 막기 위해, "반드시 데이터베이스 기초 공사가 먼저 완료된 것을 확인하고 웹 서버를 올려라" 하고 작업 순서 표지판을 엄격히 세워두는 것과 같습니다.

- **Environment Variables (인프라 환경 변수)**: 컨테이너 내부의 소스 코드를 하드코딩 방식으로 직접 수정하지 않고도, 컨테이너가 기동되는 런타임 시점에 도커 엔진 외부에서 동적으로 운영 인자값(데이터베이스명, 접근 비밀번호, 시스템 타임존 등)을 안전하게 주입할 수 있도록 지원하는 가상 OS 운영체제 수준의 변수 전달 메커니즘입니다.

  > 💡 비유하자면, 자물쇠(컨테이너)의 비밀번호를 바꿀 때 자물쇠 내부의 톱니바퀴 메커니즘을 쇠톱으로 잘라내어 개조하는 대신, 자물쇠 외부 다이얼을 쓱 돌려서 언제든 새로운 암호 조합(`MYSQL_PASSWORD`)을 간편하게 세팅해 분양하는 것과 같습니다.

### 5. 무엇을 배웠는가 (Takeaway)

- **회고(Retrospective)**: 웹 서비스와 데이터베이스가 물리적으로 결합해 있던 과거 아키텍처와 달리, 각 기술 단위를 컨테이너로 철저히 분리(Decoupling)하고 이를 Docker Compose 명세서 단 한 장으로 연동해 내는 모던 가상화 방법론의 강력함을 깊이 깨달았습니다. 만약 이 인프라 유기적 연동 기법을 수동으로 진행했다면 가상 IP 매핑과 포트 결합 오류로 밤샘 작업을 반복했을 것입니다.

- **Pain Point**: 실무 멀티 스택 환경에서 가장 빈번하게 발생하는 휴먼 에러는 데이터베이스 환경 변수 파일의 오타나 볼륨 경로 미스매치입니다. 데이터 보존 경로인 `/var/lib/mysql` 매핑이 누락된 채로 배포 파이프라인이 롤백되거나 컨테이너가 교체되면 고객의 소중한 비즈니스 데이터가 영구 유실되는 대형 재앙이 발생합니다. 선언적 IaC 스크립트를 통해 스토리지와 계정 정보를 일목요연하게 코드로 통제하는 형상 관리 습관이 현장 엔지니어에게 얼마나 무거운 책임감이자 강력한 무기인지 직관하게 되었습니다.

- **성장 포인트**: 개별적인 단일 도커 컨테이너 기동 단계를 넘어서서, 다중 레이어 아키텍처(Multi-tier Architecture)의 인프라 흐름을 거시적인 관점에서 설계하고 조율할 수 있는 '주니어 아키텍트'로서의 시스템 엔지니어링 역량을 단단하게 확보하게 되었습니다.
