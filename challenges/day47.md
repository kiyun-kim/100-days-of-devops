## 📅 Day 47: Python 애플리케이션 도커라이징 및 호스트 포트 바인딩 배포

### 1. Task

- **요구사항**: Nautilus DevOps 팀의 Python 애플리케이션 서비스화 계획에 따라, 제공된 의존성 명세서(`requirements.txt`)와 소스 코드를 내포한 경량형 가상 컨테이너 이미지를 빌드하고, 외부 네트워크와 안전하게 통신할 수 있도록 라우팅 포트를 구성하여 실환경에 배포합니다.

- **목표**: Stratos DC 내부의 Application Server 1 (`stapp01`) 환경에 접근하여 지정된 이미지 사양과 네트워크 경로 요구사항을 완벽하게 만족하는 컨테이너 환경을 구축합니다.
  1. 대상 서버인 App Server 1 (`stapp01`)에 SSH 원격 접속을 수행합니다.
  2. `/python_app/Dockerfile` 경로에 애플리케이션 컨테이너 패키징 설계를 선언합니다.
  3. `python:3.9-slim` 베이스 이미지를 기반으로 의존성 라이브러리를 설치하고, 컨테이너 내부 수신 포트를 `3003`으로 지정합니다.
  4. 생성할 이미지 명칭을 `nautilus/python-app`으로 지정하여 정상 빌드합니다.
  5. `pythonapp_nautilus`라는 이름의 컨테이너를 생성하여 호스트의 `8099` 포트와 컨테이너 내부 `3003` 포트를 매핑하여 기동합니다.
  6. 배포 완료 후 `curl` 호출을 통해 애플리케이션 서비스 수신 상태의 최종 무결성을 검증합니다.

---

### 2. Workflow

```text
  [ External Traffic / Engineer ]
              │ (TCP Port 8099)
              ▼
  [ App Server 1 (Host: stapp01) ]
              │
              │ (Port Forwarding: 8099 -> 3003)
              ▼
  [ Docker Daemon ]
              │
              └── [ Container: pythonapp_nautilus ]
                      │
                      ├── Image: nautilus/python-app
                      ├── App Context: /app (src/server.py)
                      └── Service Runtime: Python (TCP Port 3003)

```

### 3. 해결 과정 (Action)

#### 3-1. App Server 1 원격 접속 및 Dockerfile 설계

인프라 관리 대상 서버인 App Server 1에 안전하게 접속한 후, 소스 코드가 위치한 작업 경로로 이동하여 경량화 배포용 Dockerfile을 생성합니다.

```bash
# Jump Host에서 App Server 1 서버로 SSH 원격 접속 실행
ssh tony@stapp01

# 파이썬 소스 및 의존성 파일이 위치한 디렉터리로 이동
cd /python_app

# 가상 이미지 패키징을 위한 Dockerfile 생성 및 명세 작성
sudo vi Dockerfile

```

```dockerfile
FROM python:3.9-slim

# 컨테이너 내 작업 디렉터리를 고정하여 경로 일관성 확보
WORKDIR /app

# 호스트의 현재 컨텍스트 내 소스 파일 전체를 컨테이너 내부로 안전하게 복사
COPY . .

# 의존성 명세 파일을 참조하여 가용 라이브러리를 캐시 없이 청결하게 설치
RUN pip install --no-cache-dir -r src/requirements.txt

# 애플리케이션이 통신할 컨테이너 내부 네트워크 포트 명시
EXPOSE 3003

# 컨테이너 구동 시 파이썬 웹 서버 데몬을 기동할 진입 명령어 선언
CMD ["python", "src/server.py"]

```

- **설정 변경 의도**: 보안 및 컨테이너 용량 최적화를 위해 경량 이미지 버전인 `slim` 계열을 채택했습니다. 빌드 런타임 중 종속성 캐시가 축적되지 않도록 `--no-cache-dir` 옵션을 활용하여 효율성을 높였으며, 기동 스크립트(`server.py`)의 상대 경로가 틀어지지 않도록 `WORKDIR` 기준점과 `CMD` 파라미터를 정밀하게 매핑했습니다.

#### 3-2. 도커 이미지 빌드 파이프라인 가동

작성된 파일 아키텍처를 기반으로 도커 엔진의 빌드 콘텍스트를 호출하여 정식 패키징 이미지를 생성합니다.

```bash
# 지정된 도커 이미지 명칭 및 태그 형식을 적용하여 로컬 빌드 수행
sudo docker build -t nautilus/python-app .

```

#### 3-3. 애플리케이션 컨테이너 백그라운드 배포

생성이 완료된 `nautilus/python-app` 이미지를 실구동 자원으로 격리하여 인프라 네트워크 상에 영구적으로 배치합니다.

```bash
# 컨테이너 식별명을 고정하고 호스트 포트 8099와 내부 3003 포트를 물리 결합하여 백그라운드 구동
sudo docker run -d --name pythonapp_nautilus -p 8099:3003 nautilus/python-app

```

#### 3-4. 엔드포인트 바인딩 상태 및 런타임 트래픽 최종 검증

도커 프로세스의 업타임 상태를 확인하고, 호스트의 루프백(localhost) 주소로 직접 HTTP 요청을 송출하여 애플리케이션의 정상 응답 유무를 최종 점검합니다.

```bash
# 가동 중인 컨테이너 리스트 및 8099->3003 포트 포워딩 규칙 바인딩 재확인
sudo docker ps

# 로컬 엔드포인트를 호출하여 xFusionCorp Industries 환영 메시지 수신 상태 검증
curl http://localhost:8099/

```

### 4. 핵심 개념 정리

- **호스트 포트 바인딩 배포**: 도커 컨테이너 환경에서 격리된 내부 서비스를 외부 네트워크와 연결하기 위해, 물리적인 호스트 서버의 특정 포트와 컨테이너 내부의 포트를 논리적으로 이어주는(바인딩) 방식을 의미합니다.
  - **호스트 서버**: 대형 아파트 단지 본관
  - **컨테이너**: 아파트 단지 내에 격리되어 입주한 특정 회사 사무실
  - **호스트 포트 (8099)**: 아파트 본관 외벽에 설치한 외부 직통 전화기 번호
  - **컨테이너 포트 (3003)**: 회사 사무실 책상 위에 놓인 내부 내선 전화기 번호

  > 💡 거대한 아파트 단지의 대표 전화번호와 내선 번호 관계와 같습니다. 외부 고객(사용자)이 아파트 내부 사정을 모르는 상태에서 격리된 사무실로 연락을 취하려면, 오직 아파트 외벽에 공개된 직통 전화번호인 8099로 전화를 걸어야 합니다. 그러면 아파트 교환기(도커 데몬)가 이 전화를 받아 사무실 책상의 3003번 내선 번호로 즉시 선을 연결(바인딩)해 주는 것과 같은 원리입니다.

- **`EXPOSE` 지시어**: Dockerfile 내에 선언되어 이 이미지를 기반으로 생성될 컨테이너가 런타임에 외부와 통신할 네트워크 포트를 문서화 및 명시해 주는 메타데이터 선언 명령입니다. 그 자체로 포트를 물리적으로 오픈하거나 방화벽을 해제하지는 않습니다.

  > 💡 비유하자면, 새로 지은 회사 건물 도면(이미지)에 "이 방은 외부 전화선 연결용 3003번 콘센트가 위치할 자리입니다"라고 설계도면 상에 인쇄해 두어, 차후 인테리어 시공업자(사용자)가 헷갈리지 않고 외부 전화선(`-p`)을 올바른 자리에 연결할 수 있도록 이정표를 남기는 것과 같습니다.

- **`CMD` 지시어 (명령어 파라미터)**: 도커 이미지가 빌드를 완료하고 최종적으로 컨테이너화되어 기동되는 시점에, 운영체제(OS) 환경 위에서 기본적으로 실행해야 할 단일 프로세스의 메인 실행 명령과 인자값을 정의하는 지시어입니다. Dockerfile 내에서 단 한 번만 유효성을 가집니다.

  > 💡 비유하자면, 장난감 자동차(컨테이너)의 태엽을 끝까지 감아 바닥에 내려놓는 순간, 자동차가 알아서 앞으로 전진(`python src/server.py`)하기 시작하도록 사전에 내장해 놓은 메인 구동 모터 스위치와 같습니다.

- **`pip install --no-cache-dir`**: 파이썬 패키지 매니저(`pip`)를 통해 라이브러리를 설치할 때, 다운로드한 패키지 압축 파일이나 임시 빌드 파일들을 로컬 스토리지 캐시 디렉터리에 잔존시키지 않도록 강제하여 도커 이미지 레이어의 용량을 최소화하는 빌드 최적화 옵션입니다.

  > 💡 비유하자면, 밀 키트 박스(도커 이미지)를 구매해 음식을 조리해 담을 때, 완성된 요리만 깔끔하게 용기에 담고 재료를 감싸고 있던 비닐봉지와 껍질(캐시 파일)은 박스 안에 남기지 않고 즉시 쓰레기통에 폐기하여 박스의 무게와 부피를 최소한으로 줄이는 가볍고 청결한 정리 방식과 같습니다.

### 5. 무엇을 배웠는가 (Takeaway)

- **회고(Retrospective)**: 단순한 웹 서버 아키텍처 배포를 넘어 파이썬 런타임 언어 기반의 소스 코드를 직접 컨테이너화(Dockerizing)하고 라이브러리 의존성 체계를 인프라와 결합하는 과정을 수행하며, 모던 애플리케이션의 컨테이너 배포 구조를 완전하게 숙지하게 되었습니다. 배포 명세에 따른 작업 디렉터리 제어와 빌드 최적화 메커니즘을 미리 다뤄보지 않았다면 불필요한 레이어 증설로 인해 스토리지 비용 낭비를 초래했을 것입니다.

- **Pain Point**: 실무 환경에서 파이썬이나 노드와 같은 런타임 서비스를 도커라이징할 때 가장 자주 일어나는 휴먼 에러는 `COPY` 지시어 작동 이후의 작업 경로(`WORKDIR`) 미스매치나 의존성 파일 유실입니다. 경로 설정을 명확히 구조화하지 않은 상태로 파이프라인을 기동하면, 빌드는 성공한 것처럼 보여도 컨테이너가 구동하자마자 파일 부재로 즉시 붕괴(`CrashLoopBackOff`)하는 심각한 배포 장애로 이어집니다. 코드의 통제권이 엔지니어의 정확한 경로 설계로부터 시작된다는 점을 깊이 이해했습니다.

- **성장 포인트**: 단순히 남이 만들어 놓은 이미지를 가져다 쓰는 수동적 엔지니어링 수준에서 탈피하여, 개발 팀이 작성한 가공되지 않은 소스 자산을 컨테이너 규격에 맞게 변환하고 아키텍처 포트 포워딩 라인까지 완결 짓는 진정한 인프라 자동화의 주역으로 한 차원 성장하게 되었습니다.
